## 本设计建议采用

| 项目 | 设计选择 | 原因/影响 |
| --- | --- | --- |
| 导航 | 衣橱、搭配、日历、我的 | 高频操作直接到达，其余集中在我的 |
| 画布 | 自动排版+移动/缩放/旋转/层级 | 提供完整搭配操作，需验证微信触控与导出 |
| 穿着口径 | 每衣物每天至多计1次 | 兼容同一天多个场景，避免次数虚增 |
| 删除 | 归档保历史；无引用才能永久删除 | 引用和图片保留规则可解释 |
| 分享 | 用户主动导出搭配图片 | 数据仍各自独立 |
| 入会 | 一次性邀请码绑定微信身份 | 适合少量固定成员 |
| 图像任务 | Node.js单任务worker + PG阶段结果，调用New API | 分别保留识别与抠图结果，重试只补失败部分 |
| 图片后处理 | 使用已有sharp统一透明画布与缩略图 | 尺寸由应用保证，模型效果由真实照片验证 |
| 用户上传 | 10MB/2400万像素/批次20张 | 初始资源约束，需真机图片验证 |
| 备份 | 每日备份，保留7天，至少一份异地 | 恢复能力依赖位置与演练 |

## 需要特别避免的误判

- 面板CPU空闲是单时点观测，不能证明图片后处理峰值资源足够。
- 原型服装插画和成功结果是示例，不能用来宣称抠图或识别准确率。
- 微信登录验证身份，成员准入与资源归属仍由后端执行。
- 前端与后端各自有输入边界，双端校验并不等于同一内部流程重复校验。
- 只持有短期图片链接的人在有效期内可以访问该资源，签名URL需按凭证保护。

## 评审次序

先确认产品规则与视觉方向，再确认图像能力测试结果、外部服务和费用，最后冻结实现契约。变更需同步需求、页面、数据、接口和验收条目。
