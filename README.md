# 搭搭不搭搭

微信原生衣橱小程序，后端使用 Express 与 PostgreSQL。当前工程提供本地开发与测试流程，衣橱、搭配、日历、清单、天气推荐与后台图像任务已接入接口；天气及外部 AI 服务的条件见下文。最新验证范围见 [本地验证记录](docs/local-verification.md)，产品规则与原型见 [设计文档](docs/design/README.md)。

搭配页分为「穿搭」和「搭配」两个页内 Tab，默认进入「穿搭」查看本周穿搭、可展开月历与所选日期的穿搭记录；「搭配」展示搭配库，支持自定义新建、搜索、分类与收藏筛选。支持同日多条记录，未来日期不可登记实际穿着。搭配分类独立维护，可新增、筛选，并在新建和详情页选择；分类与收藏可组合筛选。旧搭配在升级后为未分类，原有场景、布局和穿搭记录保留。首页展示实况天气、推荐单品与推荐穿搭，支持展开三日预报、切换城市和定位；中央「+」用于添加衣物。

## 本机启动

使用 Node.js `24.22.3`、npm `11.19.1`、Docker 和微信开发者工具。本次工作区已下载的 Node 位于 `.local-tools/node-v24.22.3-darwin-arm64/bin/`，新终端可先执行：

```sh
export PATH="$PWD/.local-tools/node-v24.22.3-darwin-arm64/bin:$PATH"
export npm_config_cache="$PWD/.local/npm-cache"
```

在项目根目录执行：

```sh
npm ci
npm ci --prefix miniprogram
npm run configure
npm run db:up
npm run dev
```

前后端分别保留锁文件。小程序依赖安装在 `miniprogram/node_modules`，便于微信开发者工具发现；后端依赖安装在根目录。`.env`、图片、下载的运行时和构建产物均被 Git 忽略。

`npm run configure` 首次创建本机 `.env` 并生成随机媒体签名密钥；随后根据 `.env` 中的 AppID 生成 `project.config.json`。请在本机 `.env` 填写 `WECHAT_APP_ID`，在微信公众平台生成 AppSecret，只填入 `.env` 的 `WECHAT_APP_SECRET`，修改后重启 API。前端通过 `wx.login` 获取 code，后端使用 AppSecret 向微信校验身份。

API 默认监听 `http://127.0.0.1:3006`；`npm run dev` 同时启动 API 和任务 worker。API 与 worker 启动时自动校验和执行 SQL 迁移。

```sh
curl http://127.0.0.1:3006/api/health
npm run invite
```

邀请码为一次性、72 小时有效。首次微信登录后填写邀请码，默认成员上限为 3 人。登录后昵称仍为默认值或尚未设置头像时，会进入个人资料页，也可跳过；资料完整时直接进入首页。微信登录凭证不含昵称和头像，用户通过微信头像选择按钮与昵称填写框主动提供资料，保存到自己的账号后在“我的”展示，点击头像或昵称可继续修改。

## 微信开发者工具

源码工程统一通过**项目根目录**的 `project.config.json` 导入，`miniprogram/` 作为小程序源码目录。本次验证工具版本为 `2.02.2609250 Stable`，基础库为 `3.18.0`，工程配置固定此基础库版本。

开启本机服务端口后，在项目根目录执行：

```sh
npm run build:wechat
```

此命令先调用官方 CLI 构建 TDesign，再用 `esbuild@0.28.2` 打包 `zod@4.6.7`，并将所有 npm JavaScript 依赖统一转译为 ES2015 CommonJS，避免微信上传校验无法解析 `??`、`?.`。官方 npm 构建器不能直接识别 Zod 的 `.cjs` 入口，过程中该入口的 warning 由随后步骤处理。完成后点击开发者工具“编译”。手动执行“构建 npm”后，也要运行 `npm run build:wechat-deps` 转译全部依赖。

CLI 默认路径为 `/Applications/wechatwebdevtools.app/Contents/MacOS/cli`；其他安装位置通过 `WECHAT_CLI` 环境变量指定。TypeScript 使用开发者工具的 `useCompilerPlugins: ["typescript"]` 配置。

本地工程使用 `miniprogram/config/environment.ts`，默认 API 为 `http://127.0.0.1:3006/api`；后端 `npm run dev` 读取项目根目录 `.env`，其中数据库、媒体目录和 `PUBLIC_BASE_URL` 均为本地配置。本地调试打开项目根目录，生产工程打开 `release/wechat/`，两者独立。手机无法访问电脑的 `127.0.0.1`；本地真机联调时将本地前端地址改为电脑局域网地址，并相应修改本地 `HOST`、`PUBLIC_BASE_URL` 和微信域名配置。

## AI 衣物整理

一次选择最多 20 张照片，先在预览页查看全部缩略图，逐张或批量标记“单件 / 套装”。点击“开始识别”后才上传和入队；选图、切换模式与媒体上传本身不会调用 AI。单件创建一件草稿，套装先定位再创建各件草稿。提交后可离开小程序，worker 继续处理。单件直接进入衣物编辑页并确认入橱；套装在“处理与审核”中按来源照片集中核对、补拍和确认。

已有处理图的衣物可选择“修补当前图片”：同时传当前处理图（修改底图）和原图（结构参考），填写要修补的部位，仅生成新的透明单品图，保留衣物资料和已有分类核对建议。“从原图重新识别”独立保留，用于重新定位目标并更新资料及单品图。修补失败时保留原有图片；重试沿用本次选择的两张图。

这两个入口的描述框支持按需“优化描述”：使用识别模型、`reasoning_effort=none`，只传文字和当前衣物已保存的名称、分类及特征，不传图片。结果回填后可继续编辑，仍需点击“开始修补/开始识别”才创建处理任务；描述不明确时提示补充信息。单次优化超时 8 秒，不自动重试，失败时保留原输入，可直接提交原描述。

在 `.env` 中配置：

```dotenv
NEW_API_BASE_URL=https://newapi.ammmm.us/v1
NEW_API_KEY=你的服务端令牌
AI_RECOGNITION_MODEL=gpt-6-luna
AI_CUTOUT_MODEL=gpt-image-2.6-flare
AI_CUTOUT_QUALITY=low
AI_CUTOUT_COMPLEXITY=low
```

定位与资料识别通过 `/chat/completions`，固定 `reasoning_effort=medium`、JSON 输出，token 预算分别为 2048 / 4096。识别直接读取原图，套装成员另带目标局部图。单件与套装成员均通过 `/images/edits` 按原图和目标描述直接生成透明 PNG，去除人体、背景与覆盖水印，合理补全被遮挡的衣料；移除交叉手臂后延续裙身，保留真实领口、袖口和镂空。识别与图片生成并行，每个阶段各调用一次。整套图另行去除背景、人台和支架，保留叠穿关系。隐藏结构属于推测，需在审核时核对。旧任务已保存的黑白遮罩仍按原图像素合成后继续处理；没有可复用遮罩的重试使用新的透明图生成流程。默认识别超时 60 秒、抠图超时 180 秒，可通过 `.env.example` 中对应字段调整。如果图片接口返回 URL，须在 `AI_IMAGE_DOWNLOAD_HOSTS` 中配置下载域名，多个用英文逗号分隔；base64 返回无需此配置。

排队和处理期间禁止修改、删除衣物，前后端同时限制。处理结束后自动填好名称、二级分类、色系、具体类型、颜色描述、图案、可见特征、季节及已有风格/场景标签。失败或部分成功保留可用结果，结束后可以编辑，重试只补未完成的阶段。上游调用结果未知时暂停重复调用，需先核对 New API 记录。

DNS、连接建立或 TLS 握手阶段明确未发送的失败可直接重试；超时或发送后断连仍标为结果未确认。衣物编辑、套装审核和独立任务卡片提供“核对后重试”，确认 New API 调用已结束并接受再次计费的可能后，仅重试未完成阶段。确认记录与原始异常保留在原任务，新任务使用同一原图、修补底图及提示词。网络提交失败后重试沿用同一请求编号，避免重复入队。服务端按任务和阶段记录异常类型、错误代码及上游请求编号，不记录密钥或图片内容。

衣物编辑页点击“重新抠图与识别”可查看原图，并填写最多 300 字的补充描述，例如“只识别里面的深灰色背心，排除外面的开衫”。描述可留空，随任务保存并在下次重新识别时带出；同一描述用于资料识别与单品图处理，有描述时从整张原图定位，颜色和款式仍以照片为准。主动重新识别更新识别字段与单品图，补拍继续保留手改资料；失败重试沿用原描述并复用成功阶段，修改描述后开始新的完整处理。

衣橱的「批量整理」可选择最多 50 件衣物，统一修改分类、色系、季节、图案、品牌、尺码、面料、场景和风格；场景与风格支持多选添加、移除或按类型替换，其余资料保持不变。批量删除需确认，所选衣物有版本冲突、仍在处理或被搭配、穿搭记录、清单引用时整批回滚。处理结束的待核对衣物可在核对页直接删除，无需先确认入橱。

品牌、面料、服装尺码和鞋码在“我的 → 分类与标签”中独立维护，衣物资料从维护项选择。服装尺码如 S、M、L、XL，鞋码如 36、37、38；选择分类后只展示对应分组，跨组更换分类会清空原尺码。一级分类可设置尺码分组，二级分类继承；分类改名不影响分组。已有尺码会按衣物分类拆分并保留关联，未使用的纯数字尺码归入鞋码，其余归入服装尺码。

新用户默认创建 11 个一级分类：上衣、外套、裤子、裙子、连衣裙、鞋靴、箱包、配饰、眼镜、帽子、其他，不预置二级分类。分类管理仍支持新增大类或在大类下新增品类，如“上衣 / 针织开衫”；选择大类可筛选其所有二级品类。AI 根据照片独立推断二级品类，并在所选一级分类下语义匹配已有二级分类；匹配时复用，没有合适项时回填一级分类并在核对页建议新增。用户可修改建议名称，选择“采用建议”或“暂不新增”；更换一级分类或手选已有二级分类会清除原建议。确认保存时，新增分类与衣物关联在同一事务内完成；同一大类下同名分类直接复用，其他分类占用名称时提示修改，不自动移动分类。自动处理结果保持草稿状态，核对并确认后进入日常衣橱。

上传前等比缩小至最长边 2048 像素；头像为 512 像素，JPEG 使用 80 质量压缩。服务端使用 `sharp@0.35.5` 将透明结果规范化为 1024×1024 PNG、主体放入 896×896 区域，生成 480×528 范围内的透明 WebP 缩略图。原图与处理图均保留，可在核对页对比选择。

衣橱提供“单品 / 套装”栏目；套装独立保存整套图和成员，单品详情可查看所属套装与其他成员。套装至少两件，一件最多属于一个套装；解散仅解除关系，删除或移出至不足两件时自动解散，其余衣物保留。整组确认在同一事务完成，补拍和重试保留已手改的资料。V10 只增加录入、套装及关联结构，历史衣物默认无套装。

图像队列由独立 Node.js worker 处理，无需安装本地模型。照片依次处理，同图最多并行两件，每件的识别与图片请求并行，同时生成一张整套透明图；单件无需定位。整套图失败可单独重试，保留原图和已有单品结果；手动更换整套图后，后台结果不会覆盖该选择。V11 只增加任务类型约束，不修改或自动重跑历史记录。最新流程与验证见 [多件衣物识别与套装](docs/design/13-multi-item-import-and-clothing-sets.md)。天气通过高德 Web 服务 API 查询，在 `.env` 中填写 `AMAP_KEY`，Key 平台类型选择“Web 服务”。

首页优先自动获取微信位置；位置不可用或无法解析城市时，改用高德 v3 IP 定位识别大致城市，再用行政区编码查询天气。IP 识别仅支持国内公网 IPv4；本地、私网、IPv6 或无法识别的 IP 会结束自动获取流程，用户可点击卡片城市手动选择。点击城市可输入中文、拼音或空格分隔的省份与地名搜索，并分页展示行政归属。目录来自[高德官方行政区编码表](https://developer.amap.com/api/webservice/download)，包含 3211 个城市、区县及直辖市/特别行政区地点，保存在 `server/src/weather-locations.ts`；检索不调用外部接口，不需要密钥。目录覆盖不代表每个地区都有天气数据，无预报时会明确提示。

自动定位通过 `wx.getLocation` 获取 GCJ02 经纬度，由高德逆地理编码解析行政区编码，再查询天气。位置和手选结果不写入用户资料或本地缓存。微信定位使用前需在微信公众平台“开发管理 → 接口设置”开通 `wx.getLocation` 接口，在用户隐私保护指引中声明地理位置信息用于查询当地天气；`app.json` 已配置权限用途及 `requiredPrivateInfos`。IP 查询与手选城市无需微信定位接口权限，微信授权与真机定位仍需在对应 AppID 下验收。

天气接口分别请求 `extensions=base` 的实况和 `extensions=all` 的预报。卡片展示当前气温、天气、湿度和风力；展开可查看今天、明天、后天的昼夜天气与温度，实况和预报分别显示数据发布时间。天气按查询位置缓存 10 分钟，上海时区跨日失效；点击刷新通过 `refresh=true` 绕过缓存重新查询，同日请求失败可返回标记为 `stale` 的缓存。IP 定位、逆地理编码和天气的额度及权限分别受高德账号配置限制。

## 首页天气推荐

天气加载成功后，后端分页读取当前用户已入橱且图片可用的衣物，先按天气筛选，再取最多 200 件交给 AI，生成最多 6 件单品、3 套穿搭。使用已有的分类、类型、颜色、季节、可见特征和面料资料；适合直接推荐的衣物优先于仅能内搭的短袖，同优先级按最近更新排序。单品横向浏览并可查看衣物详情；穿搭整卡左右滑动切换，显示当前序号，可进入对应搭配详情。滑动仅浏览已生成结果，不重新调用 AI；单套不自动轮播，多套滑到首尾停止。

初版温度阈值为产品筛选规则，后续可根据使用反馈调整：

- 冷天：当前气温 ≤12°C，或当天最高温 ≤15°C，或当前气温 ≤18°C 且最低温 ≤5°C/风力达到 5 级。短袖、无袖上衣只能作内搭，不进入单品推荐；每套必须有上身保暖层，明确标为薄款的外套不能单独充当保暖层。
- 偏凉：满足冷天规则，或当前气温 <18°C、最高温 <20°C、最低温 <10°C，或当前气温 <22°C 且大风。排除明确的短裤、短裙和露趾鞋。
- 更冷：满足冷天规则且当前气温 ≤5°C、最高温 ≤8°C 或有降雪，每套还需要羽绒、棉服、加绒等明确保暖特征的上身衣物。裤子和围巾不能代替上身保暖层。
- 高温：当前气温 ≥28°C 且最低温 ≥20°C，排除明确的厚衣和仅标为冬季的衣物。

晴天不会放宽低温规则，不按日历月份筛选。夏季标签辅助冷天筛选，仍保留可用的短袖内搭和有明确保暖层信息的衣物；冷天排除无法辨别品类的衣物，未知资料不推断保暖性能。AI 输出后会去掉单独推荐的冷天短袖及缺少完整上下装/连衣裙、保暖层的组合。筛选后没有合适衣物时返回「无匹配」，保留「空衣橱」状态用于没有可用入橱衣物的情况。

推荐复用现有 New API 配置，增加以下可选项：

```dotenv
AI_RECOMMENDATION_MODEL=gpt-6-luna
AI_RECOMMENDATION_TIMEOUT_MS=45000
```

`POST /api/recommendations` 仅接受 `{ "cityCode": "340800" }`，天气与用户身份由服务端确定。结果保存在 PostgreSQL 的 `weather_recommendations` 表，按用户、上海时区日期和城市缓存。气温及今日高低温变化不足 3°C、降雨/降雪/大风条件相同，且筛选规则分档、候选衣物资料与模型未变时复用；跨过温度阈值即使不足 3°C 也重新生成。本版更新缓存规则版本，旧推荐不会继续复用。并发请求由数据库锁合并，同日旧天气仅可读取已有缓存。V9 只新增此缓存表，保留现有业务数据。

首页分别展示加载、空衣橱、无匹配和错误状态；失败可重试，刷新失败时保留已加载的推荐。天气自动获取失败后，用户可点击城市手动选择。

## 出行清单与微信提醒

清单分为「进行中」与「历史」。结束行程保留衣物和收拾状态，同时取消待发送提醒；可重新开启，或复制为日期待定、收拾状态清空的新行程。超过结束日期仅标记「待结束」，不会自动结束。V13、V14 新增行程状态、提醒任务与可选出发时刻，保留现有清单、日期和勾选数据，不为旧行程自动开启提醒。

在服务端 `.env` 中配置：

```dotenv
WECHAT_PACKING_TEMPLATE_ID=<微信后台已添加的出行提醒模板ID>
WECHAT_MESSAGE_ENV=formal
```

模板字段固定为 `thing1` 行程名称、`time8` 出发时间、`thing6` 出行清单；`time8` 使用出发日期和 `HH:MM` 时刻，默认 `07:00`，可在新建或编辑清单时修改。AppSecret 使用已有 `WECHAT_APP_SECRET`；开发版、体验版、正式版消息跳转环境分别设为 `developer`、`trial`、`formal`。

保存出发日期后自动安排前两天、前一天的 19:00 提醒，统一按北京时间计算。仅在创建清单或保存已更改的日期、出发时刻时按需调用微信订阅授权，日期范围选择和确认只更新草稿；既有待发提醒对应的授权可继续用于改期，额度足够时不重复申请。当前「行程提醒」模板经微信接口核实为一次性订阅，每次同意增加一次发送额度：收到两次授权安排两天，只有一次时优先安排前一天；拒绝或授权接口失败仍保存清单，未授权的通知不会发送，过期时间不会补发。修改出发日期后自动重排，清空日期取消待发任务。到时已全部收齐、行程已结束、用户已停用或已出发时不发送；空清单会提醒补充衣物。错过计划时间超过 6 小时的任务跳过。

V15 将缺失的出发时刻设为默认 `07:00`，保留用户已填写的时刻；已有待发提醒调整为出发前一天 19:00，已过期则取消，不自动增加第二次提醒。既有发送结果及清单数据保留。

API 与 worker 必须持续运行，关闭小程序不影响后台提醒。明确发送失败可在重新设置日期并保存时申请授权；网络中断等导致结果未知时不自动重发，同一出发日期也不会重新安排该次通知，以免重复通知。自动化验证使用独立数据库和本地微信接口替身；真实授权、送达与消息跳转需在对应 AppID 下验收。

## 数据与迁移

本地数据库由 `deploy/compose.local.yml` 创建：项目 `fit-or-not-local`，PostgreSQL `18.6-alpine`，仅绑定 `127.0.0.1:55436`，使用独立数据卷。本机已查询确认数据库版本为 `18.6`。

```sh
npm run db:stop
```

停止容器会保留数据卷。重新 `npm run db:up` 可继续使用现有数据。

迁移位于 `server/migrations/V<版本>__<说明>.sql`。迁移器使用同一 PG 连接、advisory lock 和每文件事务，保存文件名和 SHA256。重复启动只校验历史；历史不匹配、迁移顺序错误或数据库领先于代码时拒绝启动。已执行的迁移只能通过新增迁移修正。

用户照片经鉴权获取短期签名链接；上传目录不会由前端直接访问。列表、头像及小卡片请求 WebP 缩略图，详情主图和搭配画布使用同分辨率 WebP；点击查看大图、裁剪和导出才请求原图。已有图片首次请求预览时生成 WebP 并缓存，保留透明背景，后续复用；预览文件关联原资源，沿用媒体保留和清理规则。任务保存模型版本与处理结果，后台直接写入衣物草稿，用户核对后确认入橱；更换主图会重新生成相关搭配封面。无引用媒体与孤立文件保留至少 24 小时后清理；任务仍引用的输入与结果继续保留。导出 ZIP 24 小时后过期。账号注销先撤销会话并标记，worker 随后清理。

`MEDIA_DIR` 下按用途存放新文件：`originals/` 为衣物原图与细节照，`thumbnails/` 为 WebP 缩略图，`avatars/` 为头像，`body-photos/` 为上身照，`cutouts/` 为抠图结果，`previews/` 为同分辨率 WebP 预览，`outfit-covers/` 为搭配封面，`exports/` 为导出 ZIP。数据库记录相对路径，读取、导出与清理均使用该路径；已有根目录文件继续可读，无需移动文件或修改历史数据。

## 前后端打包

完成上述依赖安装和本机配置后，在项目根目录执行以下任一命令。打包需要 Docker 运行、微信开发者工具服务端口开启；CLI 路径可通过 `WECHAT_CLI` 指定。

```sh
npm run package:production
npm run package:local
```

| 环境 | 后端目录 | 小程序工程 | 小程序 API | 镜像平台 |
| --- | --- | --- | --- | --- |
| 生产 | `release/backend/` | `release/wechat/` | `https://fabric.wapiti.vip/ootd/api` | `linux/amd64` |
| 本地 | `release/local/backend/` | `release/local/wechat/` | `http://127.0.0.1:3006/api` | 当前机器对应的 Linux 架构 |

每次更新固定目录，版本自动读取根目录 `package.json`，写入归档文件名、镜像标签和 `release.json`。生产镜像标签为 `fit-or-not-backend:<版本>`，本地为 `fit-or-not-backend:<版本>-local`；生成的 `compose.yml` 自动使用对应标签。升级版本可执行 `npm version patch --no-git-tag-version`，同步更新根目录版本及锁文件，再执行打包命令。

默认流程只执行类型检查、前后端构建、归档和生成 SHA256 校验和。它不启动应用容器、不运行集成测试、不检查容器内部或服务器版本；集成验证仍可按需单独运行 `npm test`。类型检查或构建失败时立即停止。

小程序业务代码和 npm 依赖转译为 ES2015 CommonJS，生产配置仅写入生产产物，本地源码配置保持独立。可在微信开发者工具直接导入表中对应的小程序工程。归档与总校验和保存在各自输出根目录：生产为 `release/`，本地为 `release/local/`。

后端目录包含压缩镜像、`compose.yml`、待填写的 `.env` 模板、部署说明、版本元数据和校验和。生产模板来自 `deploy/.env.example`；本地模板来自根目录 `.env.example`，数据库地址调整为本地 PG 容器 `fit-or-not-local-db-1:5432`。源码根目录的真实 `.env` 不会复制进包。使用本地后端包前，先在源码根目录执行 `npm run db:up`，创建本地 PG 及 `fit-or-not-local_default` 网络；修改过网络名时在部署目录 `.env` 设置 `LOCAL_NETWORK`。本地容器与源码开发服务共用端口 3006，启动前停止 `npm run dev`。

仅打包生产单个部分时可使用：

```sh
npm run package:wechat
npm run package:backend
```

## 生产部署

上传 `release/fit-or-not-backend-<版本>-production-linux-amd64.tar.gz` 到服务器并解压，进入其中的 `backend/` 目录。后端镜像包含 API、worker、SQL 迁移及 Node 依赖，连接服务器已有的 PostgreSQL。

生产配置使用部署目录中的 `.env`，模板设置 `NODE_ENV=production` 和 `PUBLIC_BASE_URL=https://fabric.wapiti.vip/ootd`；API 与 worker 均从该文件读取。现有服务器若仍有 Compose `environment.PUBLIC_BASE_URL`，应移除该覆盖项，统一使用部署目录 `.env`，修改后重新 `up -d`。执行以下命令时，将 `<版本>` 替换为包内 `release.json` 记录的版本：

```sh
docker load -i fit-or-not-backend-<版本>-linux-amd64.tar.gz
chmod 600 .env
```

在现有 PostgreSQL 实例中准备本应用的专用数据库和账号，账号需有该库中目标 schema 的建表及迁移权限。当前代码已验证 PostgreSQL 18.6，其他版本需在目标环境验证。

编辑部署包中的 `.env`，填写 `DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`、`MEDIA_SIGNING_KEY` 和 `WECHAT_APP_SECRET`。数据库密码按原值填写，由 `pg` 直接接收；媒体签名密钥执行 `openssl rand -hex 32` 生成。API 与 worker 使用相同的数据库字段。

`DB_HOST` 默认是 `1Panel-postgresql-i3Ey`，`PANEL_NETWORK` 默认是 `1panel-network`。API 与 worker 加入该已有网络，通过数据库容器名连接 PG；若服务器网络名不同，修改 `PANEL_NETWORK`。`DB_NAME` 默认是本应用专用库 `fit_or_not`，需提前创建并授权给 `DB_USER`。然后启动：

```sh
docker compose -f compose.yml up -d --wait
docker compose -f compose.yml exec api node deploy/start.mjs invite
```

Compose 启动 API 与 worker，并提供两者共用的媒体卷。应用连接 `.env` 中 `DB_*` 字段指定的 PostgreSQL，自动创建和升级本应用的表；数据库本身需提前准备。API 自动迁移成功且健康后，worker 才启动；迁移不匹配时服务拒绝就绪。升级前先在原部署目录执行 `docker compose -f compose.yml stop api worker`（旧包文件名为 `compose.production.yml` 时使用该文件），再备份目标数据库与媒体卷。导入新版镜像，使用新包生成的 `compose.yml` 并重新 `up -d --force-recreate --wait`；保留原有部署目录、生产 `.env`、Compose 项目名及媒体卷，勿用包内模板覆盖。当前生产版本为 0.1.6，包含 V1–V16 迁移；应用版本与迁移版本独立。历史 V8 按此前授权一次性清空测试业务数据（含会话和邀请码），保留用户资料、头像资源及迁移历史，并为现有账号重建 11 个一级分类、不预置二级分类；迁移成功后正常重启不会再次清理。V4 会将旧品牌、尺码、面料文字转换为关联字段并删除旧列，因此旧进程必须在迁移前停止；需要回退数据库结构时应恢复对应备份。验证结果见 [0.1.6 发布验证](docs/release-0.1.6.md)。

在 `fabric.wapiti.vip` 的 HTTPS 反向代理中配置 `location ^~ /ootd/`，使用 `proxy_pass http://127.0.0.1:3006/;` 去掉 `/ootd/` 前缀，例如 `/ootd/api/health` 转发为 `/api/health`，并允许至少 12 MiB 请求体。当前服务器 OpenResty 使用 host 网络，可访问宿主机回环地址；反代若使用桥接网络并加入同一个 `PANEL_NETWORK`，目标使用 `http://fit-or-not-api:3006/`。不公开媒体目录。微信公众平台的 request、uploadFile、downloadFile 合法域名均配置 `https://fabric.wapiti.vip`。微信真机和备份恢复仍需部署后验收。

IP 城市识别使用 Express `req.ip`。直连时 `TRUST_PROXY` 留空，不采信客户端传入的代理头；使用反向代理时，在部署目录 `.env` 的 `TRUST_PROXY` 填写 API 实际看到的可信代理 IP 或 CIDR，多个用英文逗号分隔。API 直接接收本机反代连接时可用 `loopback`；经过 Docker 端口映射时，通常需要填写对应网络的网关 IP，桥接反代则填写反代地址。只配置实际代理，不填任意来源或固定跳数。

当前 OpenResty 直接接收用户请求，在上述 location 中加入 `proxy_set_header X-Forwarded-For $remote_addr;`，覆盖外来同名头。若前面还有 CDN/代理，先按其官方网段配置 OpenResty real_ip，让 `$remote_addr` 为真实客户端地址，再向 API 转发。后端把确定的用户 IPv4 显式传给高德 `/v3/ip` 的 `ip` 参数，避免识别成服务器出口；无法取得可用 IPv4 或没有城市结果时返回 `LOCATION_UNAVAILABLE`，允许手选城市。
